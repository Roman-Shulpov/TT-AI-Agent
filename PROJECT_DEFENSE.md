# Защита моего проекта

Говорите только о том, что проверено. На момент разработки API-ключ отсутствовал: настоящий
Chromium и цикл с test provider проверены, автономный live LLM-прогон ещё нужно выполнить.
Не выдавайте unit/integration tests за подтверждение качества модели на любых сайтах.

## Расскажите о проекте за 30 секунд

«Я сделал браузерного агента на Python. Пользователь задаёт цель обычным текстом. Программа
показывает модели компактный снимок текущей страницы. Модель выбирает один инструмент, например
клик по временному ID. Python проверяет аргументы и выполняет действие через Playwright.
После этого страница считывается заново. Есть ограниченная память, защита от циклов,
подтверждения чувствительных действий и отдельная проверка перед сообщением об успехе».

## Расскажите архитектуру за 2 минуты

«Вход — `cli.py`: настройки, задача и ответы пользователя. `Agent` в `agent.py` управляет циклом,
но сам не знает HTML сайта. `BrowserController` запускает Chromium и выполняет универсальные
действия. `ObservationExtractor` и `extract.js` выделяют видимый текст и элементы, присваивают
runtime IDs. `ContextMemory` добавляет цель, последние результаты, краткую историю и цитаты.

`OpenAIProvider` отправляет этот контекст в Responses API вместе со схемами tools.
Модель возвращает JSON-аргументы одного function call. `models.py` проверяет имя инструмента,
тип аргументов, допустимые значения и отсутствие лишних полей. `ToolExecutor` решает, требуется
ли подтверждение, затем вызывает browser layer. Ошибка не скрывается: следующий шаг видит её
и новое состояние страницы. Это позволяет менять действие, а не слепо повторять скрипт.

При `finish` я делаю новое наблюдение и отдельный вызов verifier. Если evidence не подтверждает
цель, его замечание возвращается основному Actor. Лимиты шагов, ошибок и циклов ограничивают
работу. В core нет названий demo-сайтов или workflows под конкретные задачи».

## Почему Playwright?

Он даёт асинхронный Python API, ожидание готовности элемента перед действием, управление
вкладками, frames и профилем браузера. Это удобно для интерактивного agent loop. Selenium тоже
подходит для browser automation; выбор не означает, что Selenium плох. В проекте используется
Chromium. Другие движки Playwright здесь не заявлены как протестированные.

## Почему именно такие tools?

Это небольшой словарь действий, которые встречаются на разных сайтах: переход, клик, текст,
select, клавиша, scroll, back, wait, tab. `record_fact` сохраняет evidence; `ask_user` и `finish`
управляют диалогом. Tools не содержат «найти вакансию» или «купить товар», поэтому модель должна
сама составлять последовательность. Arbitrary JavaScript и shell не доступны модели.

## Как агент понимает страницу?

Через ограниченный DOM snapshot: URL/title, visible text, роли, имена, labels, состояния и
контекст вокруг controls. Это не raw HTML и не полное accessibility tree. Скриншоты модель
сейчас не анализирует. Если смысл UI только в canvas, это ограничение текущей версии.

## Как агент понимает, куда нажать?

В observation есть, например, `s5-e4`, роль `button`, имя и окружающий текст. Модель выбирает
этот ID. Python находит связанный DOM-узел. Модель не ищет координаты и не придумывает CSS.
Если одинаковых кнопок много, помогает контекст родителя, но он ограничен и может быть неидеален.

## Почему нет hardcoded selectors?

Структура сайта заранее неизвестна. Core ищет общие HTML/ARIA controls, а не селекторы одного
домена. В `extract.js` есть универсальные селекторы вроде `button`/`input`/`[role=button]` — это
не запретные сайтоспецифичные селекторы. Названия из fixtures находятся только в тестах.

## Как работает element_id?

`s5` — номер снимка, `e4` — элемент внутри него. Extractor хранит `ElementHandle` и подпись узла.
После нового наблюдения старые handles освобождаются, ID больше недействителен. Перед action
проверяются подключение к DOM, вкладка, URL, видимость и смысл узла. Если узел заменён,
возвращается ошибка: я намеренно предпочёл re-observe потенциальному клику по замене.

## Как работает context management?

Последние 6 действий подробные, до 12 старых — короткие receipts. Отдельно сохраняются цель,
8 последних ответов пользователя и 12 точных цитат с URL. Старые страницы не копятся.
На входной JSON есть бюджет 48000 символов, а на snapshot — собственные лимиты.
Это простое детерминированное сжатие; я не называю его смысловым LLM-summary.

## Как реализован advanced pattern?

Actor + final Verifier. Actor предлагает `finish`, controller получает свежую страницу и
вызывает модель с другим prompt и схемой проверки. Отказ возвращается как feedback.
Три отказа останавливают запуск. Это отдельный запрос только при завершении, а не на каждый click.
Недостаток: reviewer и actor используют одну модель, поэтому ошибки могут коррелировать.

## Что происходит при ошибке?

Pydantic отклоняет неправильный JSON. Browser layer возвращает безопасный `ToolResult`.
Agent сохраняет ошибку и заново наблюдает страницу. Модель выбирает другое действие.
API timeout/429/5xx имеют ограниченный retry с backoff. Браузерный click автоматически не
повторяется: он мог уже сработать. После четырёх последовательных ошибок — stop.

## Что если агент зациклился?

Сравниваются action, семантический target и fingerprint страницы. Номера runtime IDs не
участвуют, потому что меняются каждый шаг. Три повтора или восемь одинаковых состояний дают
feedback «измени план». Повторная петля завершает запуск. Дополнительно есть `MAX_STEPS`.
Это эвристика: сложную петлю из разных страниц может остановить только общий лимит.

## Что если сайт изменился?

Новый snapshot отражает новый UI, и модель может выбрать другой путь. Поэтому нет необходимости
переписывать workflow под каждый CSS-класс. Но если сайт стал недоступным, требует CAPTCHA или
потерял полезную семантику, одной этой архитектуры недостаточно: нужна ручная помощь/расширение.

## Как обрабатываются динамические страницы?

Playwright ждёт actionability, навигация ждёт DOMContentLoaded, после каждого шага делается новый
snapshot. `networkidle` не используется как обязательное условие. Для краткой задержки обновления
есть ограниченный wait tool. SPA может менять DOM без изменения URL, поэтому одного URL для
stale/loop detection недостаточно: проверяются узлы и их подписи.

## Почему не отправляется raw HTML?

Он содержит слишком много scripts, CSS и технического шума. Модель должна видеть текст,
кнопки и состояние, а не исходники страницы. Ограниченный snapshot уменьшает стоимость и
латентность. Минус — часть информации приходится получать скроллом и дополнительными шагами.

## Как защищаетесь от prompt injection?

Web content обозначен как untrusted и не может менять goal. У модели нет shell, файловых
инструментов, environment или произвольного JavaScript. Ключ хранится только на стороне SDK.
Есть валидация actions, подтверждения и ограничения. Но LLM может ошибиться, а страница может
скрывать побочные эффекты — абсолютную защиту я не заявляю. Тест проверяет разделение данных,
а не доказывает устойчивость к любой атаке.

## Почему MCP не использован / где мог бы быть?

Сейчас Python controller вызывает локальные tools напрямую, поэтому отдельный transport/server
не решает необходимой задачи. MCP пригодился бы, если тот же browser service должны использовать
несколько клиентов. Можно вынести tool schemas/executor в MCP server, сохранив safety layer.
Native LLM function calling при этом остаётся способом выбора действия моделью.

## Какие ограничения проекта?

Нет vision, произвольных жестов/drag/drop, upload/download, вложенного scroll и полного a11y tree.
Нет гарантированного обхода bot protection/CAPTCHA. Safety эвристическая, память ограничена,
verifier тоже модель. Не реализованы domain sandbox и полноценные evals на большом числе задач.
Самое важное для честной защиты — live API/demo ещё нужно проверить своим ключом.

## Что бы ты сделал ещё за неделю?

Сначала небольшой набор live-задач на нескольких UI и воспроизводимые метрики. Затем улучшил
бы самые частые реальные отказы: извлечение сложных controls, поиск нужного участка страницы,
сильнее проверял evidence. Для реальных аккаунтов усилил бы policy доменов/побочных эффектов.
Vision fallback добавил бы по измеренной необходимости, а не ради названия технологии.

## Как измерять качество агента?

На фиксированных целях и начальных состояниях: доля подтверждённых успехов, число шагов,
время, tokens/стоимость, запросы к пользователю, опасные действия без разрешения и ложные finish.
Успех должен оцениваться состоянием сайта/независимой проверкой, не одной фразой модели.
Тесты регрессий дополняют такие evals, но сами не являются benchmark качества агента.

## Пять самых вероятных вопросов

1. **Модель сама запускает Python?** Нет: возвращает name + JSON; runtime валидирует и исполняет.
2. **Почему агент, а не скрипт?** Следующее действие выбирается по текущему UI и цели во время работы.
3. **Как не перепутать элемент после React render?** Одноразовый ID + pinned handle + stale checks.
4. **Где память ограничена?** `ContextMemory`, лимиты snapshot и 48000 символов входного JSON.
5. **Что подтверждает finish?** Новый observation и отдельный verifier; абсолютной гарантии нет.
