# MCP без магии

**Model Context Protocol** стандартизирует общение AI-приложения с внешними возможностями.
В этом репозитории MCP server не реализован: опциональный учебный сервер отложен до успешной
live-проверки основного агента. Для core MCP не нужен, и зависимости MCP в проекте нет.

Представьте приложение-ассистент и отдельную программу, умеющую посчитать длину строки.
Приложение не обязано знать исходный Python этой программы. Оно спрашивает список tools,
получает описание `text_length(text: string)`, отправляет аргументы и получает результат.

- **Server** предоставляет возможности: tools, resources и, при необходимости, prompts.
- **Client** подключается к server, узнаёт возможности и вызывает их от имени приложения.
- **Host** — приложение, в котором пользователь работает; оно может держать несколько клиентов.
- **Tool** — вызываемая операция с именем, описанием и schema аргументов.
- **Resource** — адресуемые данные/контекст для чтения, например справочник. Это не произвольное действие.
- **Schema** описывает форму аргументов: обязательные поля, типы, допустимые значения.
- **Arguments** — реальные значения в конкретном вызове.
- **Structured response** — результат в согласованной форме; его ещё нужно интерпретировать и проверить.

## MCP и native tool calling — разные уровни

В нашем `llm.py` LLM выбирает function name и JSON. Это **native tool calling модели**.
Python затем напрямую вызывает `ToolExecutor`. MCP определял бы, как client узнаёт tools
другого процесса и передаёт вызов server. Он не выбирает шаг за модель и не добавляет автономность.

Возможная будущая схема:

```text
LLM выбирает tool → Agent проверяет intent → MCP client
→ MCP server с policy → BrowserController → Playwright
```

Проверка sensitive actions должна оставаться на стороне исполнителя. Нельзя считать, что
сам факт вызова через MCP означает согласие пользователя. Не стоит открывать browser server
в сеть без аутентификации и ограничений доступа.

## Практическое учебное упражнение после core

1. По официальному Python SDK создайте отдельное окружение в `examples/mcp_demo`.
2. Зарегистрируйте два безопасных tools: `text_length(text)` и `add(a,b)`.
3. Создайте client: подключение → обнаружение возможностей по версии SDK → list tools → call tool.
4. Вызовите tool с неверным типом и посмотрите validation error.
5. Сравните tool schema с `TOOL_MODELS` этого проекта.

Не нужно добавлять browser доступ в самый первый учебный пример. Точные команды установки и
SDK-синтаксис сверяйте с [официальным Python SDK](https://github.com/modelcontextprotocol/python-sdk)
перед упражнением; данный проект не заявляет их проверенными и не требует этого SDK.

**Ответ на собеседовании:** «Function calling — как модель предлагает действие. MCP — как
приложение подключает и вызывает tools внешнего сервера. В моём MVP tools локальные,
поэтому прямой вызов проще. При нескольких клиентах можно добавить MCP-адаптер».

Основные роли и primitives сверены с [официальным обзором архитектуры MCP](https://modelcontextprotocol.io/docs/learn/architecture).
