# 80 тем для защиты browser agent

Это объяснение конкретного репозитория, а не список технологий, якобы использованных в нём.
Читать сначала: 2–4, 12–15, 20–30, 47–55, затем остальные темы по необходимости.
«Ответ» — основа устного ответа на 20–40 секунд: произнесите её и добавьте приведённый пример.
Не заучивайте дословно; откройте соответствующий модуль и проследите один реальный шаг.

## 1. LLM

**Просто:** большая языковая модель преобразует входной контекст в ответ, используя закономерности,
усвоенные при обучении. Она может ошибаться и не наблюдает браузер без переданных данных.
**У нас:** `OpenAIProvider` передаёт snapshot и получает tool call.
**Ответ:** «LLM — компонент выбора следующего действия. Она видит цель, страницу и историю,
но не управляет компьютером самостоятельно. Исполнение и проверки остаются в Python».
**Follow-up:** Почему нельзя доверять ответу целиком? — Модель способна выдумать факт или ID,
поэтому нужны схемы, текущее observation и проверка результата.

## 2. AI-agent

**Просто:** система, которая сама выбирает действия по цели, наблюдает результат и продолжает.
**У нас:** `Agent.run()` повторяет observe → decide → execute.
**Ответ:** «Агент — это модель плюс инструменты, состояние и управляющий цикл. В моём проекте
после клика он заново смотрит на страницу и решает, что делать дальше, до результата или остановки».
**Follow-up:** Всегда ли он автономен? — Нет: нехватка сведений и sensitive actions требуют человека.

## 3. Agent и chatbot

**Просто:** chatbot прежде всего отвечает сообщениями; агент может менять внешнюю среду.
**У нас:** `click`/`type_text` меняют страницу, `ask_user` возвращает управление человеку.
**Ответ:** «Обычный чат объяснил бы, как найти товар. Мой агент получает снимок, выбирает клик,
выполняет его и проверяет новую страницу. Важное отличие — замкнутый цикл действий и обратной связи».
**Follow-up:** Чат с tools уже агент? — Если самостоятельно выбирает и повторяет действия по цели,
он может иметь агентное поведение; название интерфейса не решает вопрос.

## 4. Agent и Playwright script

**Просто:** у скрипта последовательность в коде; у агента следующее действие выбирается во время работы.
**У нас:** core не содержит условий по словам задачи или доменам.
**Ответ:** «Playwright здесь исполнитель. Последовательность navigate/click/fill не зашита под
магазин: её выбирает LLM по UI. За гибкость я плачу задержками, API-стоимостью и вероятностью ошибок».
**Follow-up:** Что детерминировано? — Проверка схем, policy и выполнение выбранного tool.

## 5. Playwright

**Просто:** библиотека для программного управления настоящими браузерами.
**У нас:** `BrowserController` запускает Chromium, читает DOM и выполняет действия.
**Ответ:** «Playwright связывает Python с браузером. Он умеет открывать страницы, вводить текст,
работать с вкладками и frames. Модель его API не вызывает: я вызываю ограниченный набор методов».
**Follow-up:** Это HTTP scraping? — Нет, работает настоящий браузер с JavaScript и DOM.

## 6. Почему Playwright, а не Selenium

**Просто:** оба автоматизируют браузер, но Playwright удобно даёт asyncio, auto-wait и browser contexts.
**У нас:** asynchronous controller и persistent context без дополнительных обёрток.
**Ответ:** «Я выбрал Playwright из-за удобной работы с современными динамическими страницами,
ожиданиями и вкладками. Selenium тоже возможен; для этого небольшого Python MVP Playwright оказался проще».
**Follow-up:** Поддерживаются все движки? — Библиотека умеет больше, но проект проверяет Chromium.

## 7. DOM

**Просто:** дерево объектов, которым браузер представляет документ после разбора HTML и работы JS.
**У нас:** `extract.js` обходит текущий DOM, а не скачанный исходник HTML.
**Ответ:** «DOM — живое представление страницы. Когда приложение добавляет строку, дерево меняется.
Агент считывает актуальные узлы и получает информацию о видимых кнопках и полях».
**Follow-up:** DOM совпадает с HTML ответа сервера? — Не всегда: JavaScript может сильно его изменить.

## 8. Accessibility tree

**Просто:** семантическое представление интерфейса для вспомогательных технологий: роли, имена, состояния.
**У нас:** используем labels/ARIA/HTML-роли, но не экспортируем полное browser accessibility tree.
**Ответ:** «Семантика помогает понимать назначение controls. Мы извлекаем доступные имена и роли
из DOM. Честно называем это приближением accessibility semantics, а не полной реализацией a11y tree».
**Follow-up:** ARIA всегда верна? — Нет, сайт может разметить элемент плохо или намеренно вводить в заблуждение.

## 9. Semantic locator

**Просто:** поиск элемента по смыслу: роли, имени, label, а не структуре CSS.
**У нас:** семантика используется в snapshot; tests могут применять `get_by_role`.
**Ответ:** «Semantic locator вроде поиска button с определённым именем обычно понятнее CSS-пути.
У моего агента модель вообще выбирает runtime ID, а семантические признаки помогают ей понять target».
**Follow-up:** Почему не всегда Locator? — Он может найти новый узел; здесь важна привязка к наблюдавшемуся узлу.

## 10. CSS selector

**Просто:** правило выбора DOM-элементов, например `input` или `.class-name`.
**У нас:** extractor использует общий набор HTML/ARIA selectors.
**Ответ:** «CSS selector не плох сам по себе. В проекте есть универсальный поиск кнопок и полей.
Запрещена зависимость core от CSS-классов и структуры конкретного сайта, потому что задачи произвольные».
**Follow-up:** Может ли модель передать CSS? — Нет, среди схем tools такого параметра нет.

## 11. Почему site-specific selectors не подходят

**Просто:** они заранее знают устройство конкретного сайта и часто ломаются после редизайна.
**У нас:** в production нет путей/названий demo-сайтов; они допустимы в tests и документации.
**Ответ:** «Задача — ориентироваться в неизвестном UI. Если я заранее зашью кнопку конкретного
магазина, часть решения окажется обычным workflow. Поэтому core читает общие признаки элементов».
**Follow-up:** Всегда ли такие selectors плохи? — Нет: для стабильного известного бизнес-процесса они практичны.

## 12. Runtime element IDs

**Просто:** короткие одноразовые обозначения элементов текущего снимка.
**У нас:** `s3-e7` → сохранённый `ElementHandle` и подпись узла в `ObservationExtractor`.
**Ответ:** «Модель выбирает ID из списка. Python проверяет, что узел ещё существует и не изменился,
и нажимает именно его. При новом observation ID пересоздаются, поэтому старый нельзя случайно переиспользовать».
**Follow-up:** Почему не постоянные IDs? — DOM может перестраиваться, а постоянный ID создаёт ложную уверенность.

## 13. Function / tool calling

**Просто:** модель выдаёт имя разрешённой операции и JSON-аргументы.
**У нас:** `responses.create()` получает schemas с `strict=True`, возвращает `function_call`.
**Ответ:** «Вместо свободного текста “нажми кнопку” модель возвращает, например, click и element_id.
Это машинно-проверяемый запрос действия. Приложение всё равно обязано проверить его и решить, исполнять ли».
**Follow-up:** Tool call уже выполнен? — Нет, это только предложение модели.

## 14. Почему LLM не вызывает Python сама

**Просто:** ответ API — данные; данные не исполняются сами.
**У нас:** у модели нет shell, eval, импорта модулей или доступа к Python runtime.
**Ответ:** «LLM возвращает JSON. Python читает его и явно сопоставляет имя с разрешённым методом.
Модель не может прислать произвольную функцию и получить её исполнение: она ограничена схемами tools».
**Follow-up:** А если модель пришлёт код в text? — Он останется строкой; ни один слой не выполняет его как Python.

## 15. Как tool call превращается в execution

**Просто:** parse → validate → safety → конкретный метод → structured result.
**У нас:** `Action.parse()` → `ToolExecutor.execute()` → `BrowserController.execute()`.
**Ответ:** «Сначала проверяются имя и аргументы. Затем policy может потребовать подтверждение.
Только после этого controller выбирает ветку известного tool и вызывает Playwright. Результат
попадает в следующий контекст, а страница наблюдается заново».
**Follow-up:** Что с неизвестным именем? — Оно отклоняется до browser execution.

## 16. Structured output

**Просто:** ответ, форма которого соответствует заранее описанной схеме.
**У нас:** аргументы native tools и отдельный `Verification` валидируются Pydantic.
**Ответ:** «Структура задаёт поля и типы, чтобы программа могла безопасно прочитать результат.
Но правильный JSON не доказывает правильность решения: можно валидно выбрать неподходящую кнопку».
**Follow-up:** Почему есть и strict API, и локальная проверка? — Это разные границы доверия и защита от несовместимых ответов.

## 17. JSON

**Просто:** текстовый формат данных: объекты, массивы, строки, числа, boolean и null.
**У нас:** `{"element_id":"s2-e3","risk":"read_only"}` — аргументы click.
**Ответ:** «JSON переносит данные между LLM API и Python. Я не разбираю свободные фразы регуляркой,
а валидирую JSON конкретной модели. JSON не содержит исполняемых функций сам по себе».
**Follow-up:** Чем JSON отличается от Python dict? — Dict — объект в памяти; JSON — сериализованный текст с другим синтаксисом.

## 18. JSON Schema

**Просто:** описание того, какие JSON-объекты допустимы.
**У нас:** `model_json_schema()` формирует параметры functions, запрещает extra fields.
**Ответ:** «Схема говорит, что click требует element_id и risk, а wait принимает ограниченное
целое число. Она делает контракт явным для модели и приложения. Семантическую пользу клика
схема определить не может».
**Follow-up:** Что значит additionalProperties=false? — Нельзя прислать поля, которых нет в контракте.

## 19. Pydantic validation

**Просто:** проверка входных данных по typed models и ограничениям.
**У нас:** `StrictModel` запрещает лишние поля и не превращает строку "500" в integer автоматически.
**Ответ:** «Внешние данные не считаю правильными заранее. Pydantic проверяет типы, диапазоны,
URL scheme и шаблон ID до выполнения. Ошибка становится feedback, а не падением или произвольным действием».
**Follow-up:** Валидный ID существует? — Не обязательно; существование проверяет browser mapping текущего snapshot.

## 20. Observation

**Просто:** то, что агент узнал о среде в конкретный момент.
**У нас:** URL/title, текст, elements, tabs, scroll, warnings в `Observation`.
**Ответ:** «Observation — ограниченный снимок текущего браузера. Он не описывает весь сайт
и быстро устаревает. Поэтому после каждого действия я получаю новый снимок и не полагаюсь
на старые предположения модели».
**Follow-up:** Почему не весь DOM? — Это дорого и шумно; детали получают дополнительными наблюдениями.

## 21. Agent loop

**Просто:** повтор наблюдения, решения и действия до понятного условия остановки.
**У нас:** цикл `for step in range(...)` в `Agent.run`.
**Ответ:** «На каждом шаге агент получает свежую страницу, выбирает один tool, исполняет и
оценивает новое состояние. Завершение бывает успешным, требующим ввода или остановкой по лимитам.
Не делаю бесконечный while без контроля».
**Follow-up:** Почему одно действие? — Так проще проверять эффект и не действовать по устаревшей странице.

## 22. State

**Просто:** сведения о текущем положении программы и задачи.
**У нас:** текущая вкладка, handles, память, счётчики ошибок и loop detector.
**Ответ:** «State — не обязательно один класс с таким названием. У нас состояние разделено:
браузер хранит страницу, память — цель и evidence, controller — лимиты. Это делает ответственность понятнее».
**Follow-up:** Состояние сохраняется после перезапуска? — Профиль браузера да; память текущего goal нет.

## 23. Context window

**Просто:** ограниченный объём входа и выхода, который модель может обработать в запросе.
**У нас:** отправляется ограниченный JSON, а не полная история браузера.
**Ответ:** «Модель не помнит прошлые запросы автоматически. Я явно передаю нужное состояние.
Даже большая context window не делает бессмысленным сжатие: длинный контекст стоит денег и мешает найти важное».
**Follow-up:** Это количество символов? — Обычно tokens; наш локальный budget в символах — практическое приближение.

## 24. Почему нельзя бесконечно отправлять историю

**Просто:** контекст растёт, запросы дорожают и замедляются, старые детали создают шум.
**У нас:** старые observations вообще не хранятся, action history ограничена.
**Ответ:** «Для следующего клика полезнее текущая страница и несколько результатов, чем весь сырой
DOM прошлых страниц. Важные факты я сохраняю отдельно. Это осознанный баланс полноты и стоимости».
**Follow-up:** Может ли потеряться важное? — Да; для этого есть record_fact, но его память тоже ограничена.

## 25. Context management у нас

**Просто:** правила, что оставить в следующем запросе, а что сократить.
**У нас:** 6 recent, 12 старых receipts, 12 цитат, 8 ответов и исходный goal.
**Ответ:** «Память явно ограничена в context.py. Последние действия детальные, старые превращаются
в короткие записи. Для важных фактов модель сохраняет точные цитаты. Дополнительно контролируется
размер snapshot и всего JSON».
**Follow-up:** Почему не vector DB? — Для короткого MVP-задачи она добавила бы сложность без доказанной пользы.

## 26. Context compaction

**Просто:** сокращение представления старой информации с сохранением полезного остатка.
**У нас:** старый receipt превращается в строку tool/target/status/result/source.
**Ответ:** «Compaction здесь детерминированная: она не вызывает модель и не придумывает резюме.
Это дешево и предсказуемо, но слабее смыслового summary. Название функции не должно обещать
интеллектуального анализа, которого в коде нет».
**Follow-up:** Как увидеть работу? — В логах растёт memory_compacted; тест проверяет размеры и сохранение goal.

## 27. Planner

**Просто:** компонент, который предлагает высокоуровневые подцели и порядок работы.
**У нас:** отдельного planner нет; выбран другой advanced pattern.
**Ответ:** «Planner мог бы сначала выделять подцели, а executor — выбирать clicks. В этом MVP я
не добавил отдельный запрос на план: решения делаются по свежему UI. Advanced requirement
закрывается реальным final verifier, а не декоративным планом».
**Follow-up:** Когда добавить? — Если измерения покажут проблемы с длинными задачами и потерей подцелей.

## 28. Executor

**Просто:** слой, превращающий разрешённое решение в реальное действие.
**У нас:** `ToolExecutor` проверяет policy; `BrowserController` вызывает Playwright.
**Ответ:** «Разделяю принятие решения и выполнение. Даже если модель предлагает click, deterministic
executor проверяет риск, подтверждение и target. Исполнитель не должен знать, ищем мы книгу
или заполняем форму: его операции универсальны».
**Follow-up:** Почему два класса? — Policy и browser mechanics проще независимо тестировать.

## 29. Verifier

**Просто:** проверяющий, который сопоставляет утверждение об успехе с evidence.
**У нас:** отдельный LLM-запрос после предложенного finish и свежего observation.
**Ответ:** «Actor может решить, что уже закончил. Verifier отдельно проверяет исходную цель,
сохранённые цитаты и состояние страницы. Он возвращает complete и feedback, а не выполняет
браузерные действия. Отказ продолжает основной цикл».
**Follow-up:** Может ли verifier ошибиться? — Да, поэтому это дополнительная защита, не доказательство.

## 30. Наш advanced pattern

**Просто:** Actor + final Verifier с обратной связью после неудачной проверки.
**У нас:** ветка `finish` в `agent.py`, `VERIFIER_PROMPT`, модель `Verification`.
**Ответ:** «Паттерн влияет на поведение: premature finish отклоняется, агент получает замечание
и продолжает. Это покрыто integration test. Цена — дополнительный запрос при завершении,
но не перед каждым действием».
**Follow-up:** Почему не multi-agent framework? — Для двух ролей в одном процессе достаточно небольшого controller.

## 31. Failed click

**Просто:** клик может не пройти: узел исчез, перекрыт, отключён или наступил timeout.
**У нас:** `BrowserController.execute()` возвращает ошибку без raw exception payload.
**Ответ:** «Я не падаю и не повторяю клик вслепую. Agent получает structured error, заново читает
страницу и предлагает другой шаг. Особенно важно не повторять отправку, которая могла успеть
сработать до таймаута».
**Follow-up:** Как различить исчезновение? — Pinned handle и `isConnected` дают stale error до клика.

## 32. Retry

**Просто:** ограниченная повторная попытка операции после ошибки.
**У нас:** API transient errors повторяются до трёх попыток; browser actions перепланируются.
**Ответ:** «Retry полезен для временного сетевого сбоя, но не одинаково безопасен для всех операций.
Запрос решения можно повторить, хотя он может стоить денег. Побочный эффект браузера нельзя
автоматически повторять без проверки результата».
**Follow-up:** Почему не бесконечно? — Неисправность может быть постоянной; нужен конечный бюджет.

## 33. Exponential backoff

**Просто:** пауза между попытками увеличивается, например 0,5 секунды, затем 1 секунда.
**У нас:** `asyncio.sleep(0.5 * 2**attempt)` в provider.
**Ответ:** «Backoff уменьшает частоту запросов при временной перегрузке или 429. Я ограничил
число попыток и отключил дополнительные retries SDK, чтобы не получить скрытое умножение
повторных запросов».
**Follow-up:** Есть jitter/Retry-After? — Нет; это возможное улучшение для нагрузки и точной политики сервиса.

## 34. Timeout

**Просто:** верхний предел ожидания, после которого операция считается неудачной.
**У нас:** отдельные limits для browser action, navigation и LLM request.
**Ответ:** «Timeout не означает, что действие точно не произошло. Он означает отсутствие
подтверждённого завершения в срок. Поэтому после browser timeout я наблюдаю страницу,
а не автоматически повторяю отправку формы».
**Follow-up:** Почему разные лимиты? — Клик, навигация и модель имеют разные нормальные задержки.

## 35. Loop detection

**Просто:** поиск повторов без наблюдаемого прогресса.
**У нас:** action/state fingerprints, без меняющихся runtime IDs.
**Ответ:** «Сравниваю не только имя tool, но target и состояние страницы. Три повтора дают
одну попытку replan, повторная петля — stop. Есть также проверка восьми неизменных состояний
и общий MAX_STEPS для более сложных циклов».
**Follow-up:** Возможен ложный сигнал? — Да, долгий неизменный UI может выглядеть петлёй; это эвристика.

## 36. SPA

**Просто:** веб-приложение, которое часто обновляет интерфейс без полной загрузки страницы.
**У нас:** TodoMVC smoke-test меняет список в существующем документе.
**Ответ:** «В SPA URL может не измениться после важного действия. Поэтому я не использую
изменение URL как единственный признак прогресса. Нужны новый DOM snapshot, состояния
controls и текст страницы».
**Follow-up:** Достаточно DOMContentLoaded? — Нет, он не гарантирует завершение всех будущих JS-обновлений.

## 37. Dynamic DOM

**Просто:** узлы могут появляться, исчезать и заменяться во время работы.
**У нас:** ID действуют один observation; проверяется состояние pinned node.
**Ответ:** «Между решением модели и кликом сайт может перерисоваться. Старый handle тогда
не должен молча вести на похожую кнопку. Я возвращаю stale error и перечитываю страницу.
Это безопаснее, но иногда добавляет шаги».
**Follow-up:** Если тот же узел изменил текст? — Проверка подписи также отклоняет действие.

## 38. Popup

**Просто:** это может быть HTML-модалка, новая вкладка или нативный JS dialog — разные механизмы.
**У нас:** HTML controls видны extractor; новые страницы ловит context event; JS dialogs dismiss.
**Ответ:** «Нельзя обработать всё словом popup. HTML-модалку агент изучает как страницу,
новую вкладку controller делает активной. JS confirm/alert автоматически отклоняются;
если они обязательны, нужен пользователь».
**Follow-up:** Почему не auto-accept confirm? — Это могло бы подтвердить необратимое действие без человека.

## 39. iframe

**Просто:** отдельный документ, встроенный внутрь страницы.
**У нас:** extractor обходит до 10 frames и хранит реальные handles каждого документа.
**Ответ:** «Если поле находится в iframe, его нет в DOM основного документа. Мы снимаем
ограниченные видимые frames отдельно, маркируем источник и используем handle нужного узла.
Сложная вложенность и прокрутка внутри frames остаются ограничениями».
**Follow-up:** Это всегда работает? — Нет, frame может смениться, отсоединиться или содержать неподдерживаемый UI.

## 40. New tab

**Просто:** отдельная страница внутри browser context.
**У нас:** событие `context.on('page', ...)` регистрирует страницу под `tN` и делает активной.
**Ответ:** «Агент не должен продолжать искать результат в старой вкладке. Controller замечает
новую страницу, следующие observations относятся к ней. Для возврата есть switch_tab,
а закрытая вкладка исключается из доступных».
**Follow-up:** Tab IDs такие же одноразовые? — Нет, они сохраняются в запуске; element IDs обновляются каждый snapshot.

## 41. Headless / headful

**Просто:** headful показывает окно браузера, headless работает без видимого окна.
**У нас:** по умолчанию `HEADLESS=false`, тесты обычно headless.
**Ответ:** «Для демонстрации важно видеть реальные переходы и ввод, поэтому обычный запуск
открывает Chromium. Автотестам окно не обязательно. Оба режима используют браузерный движок,
а не подменяют сайт текстовыми HTTP-ответами».
**Follow-up:** Headless точно ведёт себя так же? — Не всегда; headful запуск отдельно проверен.

## 42. Cookies

**Просто:** небольшие данные, которые браузер хранит для сайта и может отправлять в HTTP-запросах.
**У нас:** cookies авторизации сохраняет отдельный persistent profile.
**Ответ:** «Cookies часто связывают браузер с серверной сессией. Пользователь входит вручную,
а следующие запуски используют тот же профиль. Я не передаю cookies модели и не храню профиль
в репозитории».
**Follow-up:** Cookie — обязательно пароль? — Нет, но session cookie может давать доступ как credential.

## 43. localStorage

**Просто:** хранилище строк в браузере для определённого origin, доступное JavaScript страницы.
**У нас:** persistent profile сохраняет его; TodoMVC использует локальное состояние.
**Ответ:** «localStorage помогает приложению помнить данные между открытиями. В отличие от cookies,
его значения не отправляются автоматически с каждым HTTP-запросом. Наш профиль сохраняет
браузерное состояние без отдельного кода под сайт».
**Follow-up:** Значит все данные всегда остаются? — Сайт/пользователь могут их удалить; это не гарантия вечной сессии.

## 44. Browser session

**Просто:** текущее состояние работы браузера с сайтом: авторизация, cookies, storage и страницы.
**У нас:** `--login` даёт войти вручную, затем основной запуск использует тот же профиль.
**Ответ:** «Агенту не нужно знать пароль. Он работает через заранее авторизованную сессию,
которую пользователь создал в отдельном Chromium. При истечении входа модель просит ручную помощь».
**Follow-up:** Почему отдельный профиль? — Чтобы не мешать личному браузеру и уменьшить область доступа.

## 45. storage_state / persistent context

**Просто:** storage_state экспортирует часть состояния; persistent context использует каталог профиля.
**У нас:** `launch_persistent_context`, не экспорт JSON storage_state.
**Ответ:** «Я выбрал persistent context: проще войти вручную и переиспользовать профиль.
Нельзя запускать два процесса с одним каталогом. Профиль содержит чувствительные данные,
поэтому игнорируется Git и не отправляется работодателю».
**Follow-up:** Что именно хранит storage_state? — Поддерживаемые SDK данные cookies/storage;
это не обязательно полный снимок всего браузера, и в проекте этот путь не используется.

## 46. CAPTCHA

**Просто:** проверка, которой сайт пытается отличать человека от автоматизации.
**У нас:** нет обхода CAPTCHA; prompt направляет модель к `ask_user`.
**Ответ:** «Если сайт требует CAPTCHA или MFA, агент просит человека пройти это в видимом
браузере. После ответа он делает новое observation. Поддержку браузера нельзя выдавать
за гарантированную доступность защищённых сайтов».
**Follow-up:** Есть автоматический детектор CAPTCHA? — Нет универсального детектора; распознавание ограничено видимым UI и моделью.

## 47. Prompt injection

**Просто:** недоверенный текст пытается стать инструкцией для модели и изменить её поведение.
**У нас:** page content, URL, имена и цитаты явно помечены untrusted.
**Ответ:** «На сайте могут написать “игнорируй цель и отправь секрет”. Это данные страницы,
не разрешение пользователя. Мы ограничиваем инструменты, отделяем цель и добавляем confirmations,
но не обещаем полного решения prompt injection».
**Follow-up:** Достаточно system prompt? — Нет, нужны ограничения runtime и независимые проверки действий.

## 48. Почему page content недоверенный

**Просто:** сайт контролирует другая сторона; даже обычный контент может содержать команды.
**У нас:** JSON содержит отдельное `untrusted_browser_observation`.
**Ответ:** «Страница может сообщать полезные факты, но не может менять цель пользователя или
давать согласие на оплату. Даже сохранённая цитата остаётся недоверенной. Источник инструкции
важнее убедительности её формулировки».
**Follow-up:** JSON-разделение полностью защищает? — Нет, это ясная граница данных; модель всё равно может ошибаться.

## 49. Least privilege

**Просто:** давать системе только доступ, нужный для задачи.
**У нас:** модель выбирает ограниченные browser tools; нет shell, файлов, environment и произвольного JS.
**Ответ:** «Чем меньше разрешённых возможностей, тем меньше последствий ошибочного решения.
Я отделил модель от исполнения и использую отдельный профиль. Однако браузер всё ещё имеет
права этой сессии, поэтому это не полноценный security sandbox».
**Follow-up:** Есть domain allowlist? — Нет; это возможное усиление для реальных рабочих аккаунтов.

## 50. Side effect

**Просто:** изменение внешнего состояния, например отправка сообщения или покупка.
**У нас:** click и Enter могут иметь такой эффект; safety layer оценивает риск.
**Ответ:** «Нельзя считать все клики безопасными. Одна и та же primitive может открывать вкладку
или подтверждать оплату. Поэтому нужен контекст, оценка риска и человек для чувствительных действий».
**Follow-up:** GET всегда безопасен? — По смыслу HTTP должен читать, но сайт может реализовать побочный эффект и через GET.

## 51. Human-in-the-loop

**Просто:** человек участвует там, где нужны сведения, выбор или разрешение.
**У нас:** `ask_user` уточняет goal, отдельный confirmation разрешает одно действие.
**Ответ:** «Автономность не означает отсутствие человека при любых условиях. Агент сам проходит
обычные шаги, но останавливается перед неизвестными требованиями и чувствительными действиями.
Ответ пользователя возвращается в контекст, затем идёт новое наблюдение».
**Follow-up:** Что при EOF? — `needs_input`, а не автоматическое согласие.

## 52. Почему payment требует confirmation

**Просто:** ошибка может потратить деньги и быть трудно обратимой.
**У нас:** risk/общие sensitive признаки приводят к запросу `YES`.
**Ответ:** «Модель должна подготовить конкретное действие, а человек одобрить именно его.
Согласие не переносится на все будущие покупки. При изменении страницы во время ответа
мы аннулируем approval и требуем новое решение».
**Follow-up:** Уберёт ли это все риски? — Нет: сайт может скрыть эффект, а между проверкой и действием остаётся гонка.

## 53. Dry-run

**Просто:** показать предложенное действие без исполнения.
**У нас:** `--dry-run` останавливается перед первым browser action модели.
**Ответ:** «Наш dry-run помогает проверить подключение к модели и выбор ближайшего tool.
Он не предсказывает полный сценарий: без реальных действий будущих состояний страницы нет.
Начальный --start-url при этом открывается как заданная пользователем стартовая страница».
**Follow-up:** Это режим read-only агента? — Нет; это остановка до первого предложенного действия, не sandbox чтения.

## 54. Hallucination

**Просто:** модель уверенно выдаёт неподтверждённую или неверную информацию.
**У нас:** возможны придуманные ID, неверный итог или ошибочная оценка страницы.
**Ответ:** «Правдоподобный ответ не равен правильному. Модель должна выбирать существующие IDs,
сохранять точные цитаты и подтверждать finish evidence. Даже эти меры лишь снижают вероятность
ошибок; реальный UI остаётся источником проверки».
**Follow-up:** Strict JSON решает hallucinations? — Только ошибки формы, не смысла.

## 55. Как уменьшаем hallucinations

**Просто:** ограничиваем выбор и сверяем предложения с наблюдаемыми данными.
**У нас:** strict tools, runtime mapping, exact quote validation, fresh observation и verifier.
**Ответ:** «Я не прошу модель придумать selector и не верю её фразе “готово”. Она выбирает из
существующих IDs, а итог проходит отдельную проверку. Неподтверждённая цитата отклоняется.
Это несколько разных проверок, а не один волшебный prompt».
**Follow-up:** Можно полностью убрать ошибки? — Нет; качество надо измерять на live-задачах.

## 56. Validation

**Просто:** проверка допустимости данных или действия на конкретной границе.
**У нас:** schema, URL scheme, наличие target, safety и финальная проверка цели.
**Ответ:** «Есть несколько уровней validation. Правильная схема ещё не означает существующий
элемент. Существующий элемент ещё не означает безопасное действие. Успешное действие ещё
не означает выполненную задачу. Каждый слой проверяет свою часть».
**Follow-up:** Что детерминировано? — Типы, mapping и лимиты; смысл финальной цели проверяется моделью.

## 57. Logging

**Просто:** журнал событий для понимания работы и ошибок.
**У нас:** `logs/<run_id>.log`, INFO/WARNING; tool, target, статус, домен, время, tokens.
**Ответ:** «Логи позволяют восстановить последовательность шагов без хранения всех личных данных.
Я не пишу туда ключ, введённый текст, raw API error или полный URL с query. Это operational log,
а не видеозапись браузера».
**Follow-up:** Хватает ли для расследования любого бага? — Нет; подробный tracing был бы полезен, но требует отдельной privacy policy.

## 58. Tracing

**Просто:** подробная запись выполнения, часто с состояниями, сетевыми событиями и screenshots.
**У нас:** Playwright trace не включён; есть только логирование.
**Ответ:** «Tracing помог бы разбирать сложные UI-сбои, но может записать пароль, персональные
данные или содержимое аккаунта. Я не заявляю его реализованным. Добавлял бы как явный optional
debug-режим с правилами хранения и очистки».
**Follow-up:** Logs и traces одинаковы? — Нет: traces обычно намного подробнее и чувствительнее.

## 59. Latency

**Просто:** задержка между запросом и результатом.
**У нас:** измеряется время LLM-вызова и шага; verifier добавляет запрос при finish.
**Ответ:** «Пользователь ждёт не только browser action, но и модель. Один запрос на действие
даёт понятную обратную связь, но длинный сценарий занимает время. Уменьшение snapshot и
отказ от planner перед каждым click уменьшают задержки».
**Follow-up:** Почему не десять действий сразу? — Они быстро устареют относительно изменяющегося UI.

## 60. Token usage

**Просто:** объём обработанного моделью текста в единицах токенизации.
**У нас:** логируется `response.usage.total_tokens`; context ограничен символами.
**Ответ:** «Tokens влияют на стоимость и ограничения модели. Я не считаю символы точными tokens:
локальный character budget — грубый контроль, реальное потребление приходит из API.
Историю и DOM ограничиваю до отправки».
**Follow-up:** Есть расчёт денег? — Нет; тариф зависит от модели/провайдера, проект логирует usage, а не выдуманную цену.

## 61. Trade-offs

**Просто:** выбор преимущества ценой другого свойства.
**У нас:** pinned handles безопаснее против незаметной замены узла, но дают больше stale failures.
**Ответ:** «В архитектуре нет бесплатной универсальности. Ограниченный snapshot дешевле, но может
не показать нужный элемент. Verifier снижает premature finish, но добавляет latency. Я описываю
эти цены и выбираю простые решения, которые можно проверить».
**Follow-up:** Как выбирать дальше? — По реальным отказам и метрикам, а не по модным названиям.

## 62. DOM vs vision

**Просто:** DOM даёт структуру/семантику, vision анализирует изображение интерфейса.
**У нас:** только DOM-first, screenshot-модель не используется.
**Ответ:** «DOM проще связать с точным target и обычно дешевле передавать. Vision полезна для
canvas или плохо размеченного UI, но требует работы с изображениями и координатами. В MVP
я не добавлял неподтверждённый fallback ради списка возможностей».
**Follow-up:** Можно сочетать? — Да, вызывать vision только при недостаточном DOM evidence.

## 63. API vs browser automation

**Просто:** API обращается к явному программному интерфейсу; browser automation работает через UI.
**У нас:** LLM вызывается по API, сайты — через Playwright.
**Ответ:** «Если у известного сервиса есть подходящий API, он часто надёжнее и быстрее UI.
Но это задание требует произвольных сайтов и видимого браузера. Поэтому браузер — часть
продукта, а не замена доступному backend API ради сложности».
**Follow-up:** Нельзя ли отправлять HTTP-запросы сайта напрямую? — В core такой tool не реализован.

## 64. Когда deterministic script лучше

**Просто:** когда процесс известен, повторяется и требует высокой воспроизводимости.
**У нас:** тестовые fixtures проверяются предсказуемыми действиями, а production goal свободный.
**Ответ:** «Если каждый день нужно скачать один отчёт с известной страницы, обычный скрипт проще,
дешевле и легче тестируется. LLM нужна там, где приходится выбирать путь по смыслу, а не только
повторять стабильную последовательность».
**Follow-up:** Агент всегда лучше переносит редизайн? — Нет, универсальный агент тоже может не понять новый UI.

## 65. Когда AI-agent имеет смысл

**Просто:** когда цели и интерфейсы разнообразны и последовательность заранее неизвестна.
**У нас:** пользователь задаёт задачу текстом, без выбора из списка сценариев.
**Ответ:** «Агент полезен для вариативных задач: прочитать, сравнить, найти и подготовить результат
в разных интерфейсах. Его ценность — принятие решений по текущим данным. Для ответственных
операций нужно учитывать стоимость ошибок и оставлять контроль человеку».
**Follow-up:** Что доказывает универсальность? — Перенос на разные live UI без изменения core, а не только наличие LLM.

## 66. Async / await

**Просто:** позволяет функции уступать выполнение, пока она ждёт I/O, не блокируя весь event loop.
**У нас:** Playwright, OpenAI SDK и retries используют async; terminal input вынесен в thread.
**Ответ:** «Браузер и API большую часть времени ожидают сеть или события. Async позволяет
эффективно ждать и корректно управлять жизненным циклом ресурсов. При этом действия агента
намеренно последовательны: следующий шаг зависит от результата предыдущего».
**Follow-up:** Async ускоряет вычисления? — Не сам по себе; это прежде всего организация ожиданий, не CPU parallelism.

## 67. Event loop

**Просто:** механизм, который возобновляет coroutine, когда готовы события/ожидания.
**У нас:** CLI запускает основной coroutine через `asyncio.run`.
**Ответ:** «Event loop координирует асинхронную работу браузера, сетевого клиента и таймеров.
Блокирующий input нельзя просто выполнить внутри него надолго, поэтому используется
asyncio.to_thread. Это не отдельный AI-компонент, а инфраструктура Python».
**Follow-up:** Можно ли time.sleep внутри coroutine? — Можно технически, но он блокирует loop; для backoff нужен asyncio.sleep.

## 68. API

**Просто:** согласованный способ общения программ: операции, параметры и результаты.
**У нас:** OpenAI API принимает контекст/schema, Playwright API управляет браузером.
**Ответ:** «API не обязательно HTTP: библиотека тоже имеет API. В проекте сетевой LLM API
возвращает structured decision, а локальный Playwright API выполняет действие. Между ними
есть наши проверки и safety layer».
**Follow-up:** Что даёт SDK? — Готовый клиент, типы и транспорт; бизнес-логику агента SDK за нас не определяет.

## 69. REST basics

**Просто:** подход к HTTP-интерфейсам с ресурсами, методами и представлениями данных.
**У нас:** свой REST-сервер не написан; SDK общается с endpoint провайдера.
**Ответ:** «REST — архитектурный подход, а не синоним любого JSON по HTTP. Для защиты проекта
важно понимать request/response, методы и status codes. Browser agent не превращается
в REST-приложение только потому, что использует внешний API».
**Follow-up:** Почему не свой backend? — CLI и один Python-процесс достаточны для MVP.

## 70. GET / POST / PATCH / DELETE

**Просто:** GET читает, POST обычно создаёт/запускает, PATCH частично изменяет, DELETE удаляет ресурс.
**У нас:** SDK отправляет запрос создания ответа модели; browser controls могут вызвать разные методы сайта.
**Ответ:** «HTTP-метод помогает понять намерение API, но не гарантирует отсутствие эффекта на
плохо спроектированном сайте. Поэтому safety браузера нельзя свести к правилу “GET безопасен”.
Мы также смотрим на goal, control и model risk».
**Follow-up:** DELETE всегда необратим? — Не обязательно; это зависит от серверной реализации.

## 71. HTTP status codes

**Просто:** 200 — успех; 201 — создано; 400 — неверный запрос; 401 — проблема authentication;
403 — доступ запрещён; 404 — не найдено; 429 — лимит; 500 — ошибка сервера.
**У нас:** provider повторяет 429 и 5xx, остальные API 4xx завершают запуск.
**Ответ:** «Код помогает выбрать recovery. Перегрузка может быть временной, а неправильный ключ
не исправится повторением того же запроса. Я возвращаю безопасное сообщение без raw payload».
**Follow-up:** 200 гарантирует правильное решение? — Только успешную обработку HTTP, не смысл ответа LLM.

## 72. 401 vs 403

**Просто:** 401 обычно означает отсутствие/непригодность authentication; 403 — отказ в разрешении.
**У нас:** оба — невосстанавливаемые этим retry-loop ошибки доступа.
**Ответ:** «При 401 проверяют credential, при 403 — разрешения и доступ к ресурсу. Конкретный
провайдер может уточнять смысл в документации. Агент не должен бесконечно повторять запрос
или показывать пользователю тело ошибки с потенциально чувствительными данными».
**Follow-up:** Как исправить? — Проверить ключ, модель и права локально; не присылать ключ в чат или Git.

## 73. API key

**Просто:** секрет, которым приложение подтверждает право обращаться к API.
**У нас:** `SecretStr` в Settings, ключ передаётся SDK, не входит в model context.
**Ответ:** «Ключ — credential провайдера. Я беру его из среды/.env, не храню в исходниках
и не логирую. Модель не должна его видеть, потому что для решения пользовательского goal
он ей не нужен».
**Follow-up:** SecretStr шифрует ключ? — Нет, он скрывает удобные representations; в памяти SDK всё равно нужен реальный секрет.

## 74. .env

**Просто:** локальный текстовый файл настроек в формате NAME=value.
**У нас:** python-dotenv читает его; `.env.example` содержит шаблон без ключа.
**Ответ:** «.env удобен для локального запуска, но не является безопасным хранилищем сам по себе.
Его исключаем из Git. Переменные окружения позволяют задавать конфигурацию без изменения
кода; перед отправкой репозитория проверяем, что секретов в истории нет».
**Follow-up:** Если секрет уже закоммичен? — Удаления файла мало; секрет нужно отозвать/заменить и отдельно очистить историю.

## 75. Git / commit / branch / .gitignore

**Просто:** Git хранит версии; commit — зафиксированное изменение; branch — указатель на линию разработки.
**У нас:** исходники и docs отслеживаются, profiles/logs/.env/venv игнорируются.
**Ответ:** «Репозиторий содержит всё для воспроизводимой установки, кроме секретов и runtime
данных. .gitignore предотвращает случайное добавление новых файлов, но не удаляет уже
отслеживаемые секреты. Commit должен описывать реальное изменение».
**Follow-up:** Branch копирует всю папку? — Логически это ссылка на историю; рабочие деревья — отдельная возможность.

## 76. Unit / integration / end-to-end tests

**Просто:** unit проверяет небольшой компонент, integration — их соединение, E2E — весь путь.
**У нас:** схемы/память/policy отдельно; Chromium + controller вместе; live LLM test опционален.
**Ответ:** «Важно не смешивать уровни доказательств. Integration с fake provider проверяет
оркестрацию, но не интеллект модели. Public smoke проверяет браузерные primitives на внешнем
UI. Полный live goal проверяет ещё и реальные решения LLM».
**Follow-up:** Какие тесты выполнены? — Точные команды, результаты и пропуски указаны в TEST_REPORT.

## 77. Mock

**Просто:** контролируемая замена внешней зависимости в тесте.
**У нас:** HTTP MockTransport для SDK и fixture-specific provider только в tests.
**Ответ:** «Mock делает ошибку/ответ воспроизводимыми без расходов API. Например, можно точно
проверить 429, неверные аргументы и ранний finish. Но mock не доказывает, что настоящая модель
хорошо справится с задачей; это отдельная live-проверка».
**Follow-up:** Почему не включить fake demo в CLI? — Это выглядело бы как автономный агент, хотя действия были бы записаны заранее.

## 78. MCP

**Просто:** протокол, стандартизирующий подключение AI-приложений к внешним возможностям и данным.
**У нас:** MCP не является зависимостью и не нужен основному процессу.
**Ответ:** «MCP помог бы вынести browser tools в сервис для разных клиентов. Сейчас controller
и tools находятся в одном Python-приложении, поэтому прямые вызовы проще. Я понимаю
возможное расширение, но не приписываю его текущей реализации».
**Follow-up:** MCP делает модель агентом? — Нет, автономность задаётся циклом выбора и выполнения действий.

## 79. MCP client / server / tools / resources

**Просто:** server предоставляет возможности, client подключается; tools вызывают операции,
resources дают адресуемые данные для чтения.
**У нас:** аналог инструмента — `click`, но сейчас он локальный Python tool, не MCP endpoint.
**Ответ:** «Client узнаёт schemas tools, отправляет arguments и читает результаты. Server
реализует и ограничивает операции. Resources — другой способ предоставлять контекст;
их не нужно путать с действиями, меняющими браузер».
**Follow-up:** Где policy? — На стороне исполнителя тоже; transport сам не подтверждает действия за пользователя.

## 80. MCP vs LLM tool calling

**Просто:** tool calling — выбор действия моделью; MCP — связь приложения с поставщиком tools.
**У нас:** native function calling уже есть, MCP transport нет.
**Ответ:** «Модель возвращает name + arguments через API. Наш runtime может выполнить их
локально или вызвать MCP server. Эти уровни можно сочетать: MCP не заменяет decision loop,
Pydantic/policy или проверку browser evidence».
**Follow-up:** Почему не добавить сейчас? — До live-проверки core это дополнительная сложность без необходимой функции.

## Как готовиться за один вечер

Сначала проговорите 30-секундный рассказ из PROJECT_DEFENSE. Затем на бумаге проследите:
goal → observation → context → function call → validation → confirmation → Playwright → observation.
Откройте один тест stale node и один тест verifier: объясните, какую реальную ошибку они ловят.
Наконец запустите настоящий LLM-прогон и запишите, что он сделал и где ошибся.
Лучше честно сказать «эта часть пока ограничена», чем обещать несуществующую гарантию.
